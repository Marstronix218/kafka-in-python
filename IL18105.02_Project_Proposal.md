## Kafka-Inspired Distributed Event Log in Python

For my semester project, I propose to build a distributed event-streaming and message-storage system inspired by Apache Kafka. I will implement the system primarily in Python and run several broker processes or Docker containers on a single laptop to simulate independent machines.

Distributed messaging systems are important because modern applications often consist of many services that need to communicate without being tightly coupled. For example, when a user places an order, separate services may need to process payment, update inventory, send notifications, and record analytics. Instead of requiring all of these services to communicate synchronously, a distributed event system allows producers to publish events and consumers to process them independently. Kafka was originally designed at LinkedIn to provide high-throughput, low-latency collection and delivery of large volumes of log data (Kreps et al., 2011).

At the moment, I understand Kafka mainly at a high level as a distributed messaging system. I do not yet understand deeply how partitioning, replicated logs, consumer offsets, acknowledgments, and leader failover interact when machines fail. By implementing these mechanisms myself, I want to understand why a distributed event system can preserve data and continue operating even when individual nodes become unavailable.

## Architecture and Research

Kafka organizes events into topics, and each topic is divided into partitions. A partition is an ordered, append-only sequence of events. Partitioning allows data and processing to be distributed across multiple brokers, while events with the same key can be placed in the same partition to preserve their relative ordering (Apache Software Foundation, 2026a).

Kafka replicates each partition across multiple brokers. Normally, one replica acts as the partition leader and other replicas follow it. Writes are directed to the leader and copied to followers. Replication allows another replica to take over when a broker fails. Kafka also distinguishes between replicas that are sufficiently up-to-date and replicas that have fallen behind, which is important when deciding which replica can safely become a new leader (Apache Software Foundation, 2026b).

I will implement a simplified version of this model myself. Each partition will have a leader and replicas. I plan to use a replication factor of three where possible and require an event to reach a configurable number of replicas before the producer receives an acknowledgment. This will let me experimentally study the tradeoff between latency, availability, and durability.

Consumers will keep track of an offset, representing their position within each partition. Kafka similarly allows consumers to commit offsets so that they can restart and continue processing from their last recorded position (Apache Software Foundation, 2026c). This also makes replay possible: a consumer can deliberately move its position backward and process previous events again.

Finally, Kafka relies on a controller that maintains the cluster's global configuration, namely which broker is the leader for which partition. In current versions of Kafka, this controller is itself a Raft cluster (KRaft). Implementing Raft is a substantial project on its own, so I will not build a fault-tolerant controller. Instead, my cluster will include a single lightweight controller process that I will assume does not fail. It will store partition-to-leader assignments, receive heartbeats from brokers, and decide which replica to promote when a leader fails. If time permits, I will store this metadata in etcd so that the controller itself becomes fault-tolerant. Everything else, including the brokers, on-disk logs, replication protocol, acknowledgments, failure detection, replica promotion logic, and producer and consumer clients, I will implement myself rather than relying on Kafka or existing messaging libraries.

## Failure Conditions and Expected Guarantees

Failure testing will be a central part of the project rather than an additional feature. I plan to test broker crashes, consumer crashes, dropped acknowledgments, delayed replication, network interruptions, and node recovery. Because handling these failures is the core of the problem, failure detection will be built in the second week of implementation, recovery will be built alongside persistence and replication, and the failure tests will be rerun at every later stage instead of being left until the end of the semester. The one component I will assume to be reliable is the controller described above.

My target final guarantees are:

- acknowledged messages should survive the failure of one broker;
- events within a partition should retain their ordering;
- if a partition leader fails, another sufficiently up-to-date replica should become leader;
- restarted consumers should resume from their committed offsets;
- retries may cause duplicate processing, but should not silently lose acknowledged events.

The last point will let me investigate at-least-once delivery and idempotency. For example, a producer may successfully send an event but lose the acknowledgment because of a network failure. If it retries, the broker may receive the same event twice. Understanding why situations like this occur is one of my main learning goals.

Kafka itself explicitly distinguishes between different delivery guarantees and allows durability to be traded against latency through acknowledgment and replication settings (Apache Software Foundation, 2026b).

## Iterative Implementation Plan

### Week 4: Distributed foundation

I will create three independently running Python brokers communicating over the network. I will also build the lightweight controller, which stores partition-to-leader assignments. Producers will publish events and consumers will retrieve them. Topics will be split into multiple partitions whose placement is determined by event keys, so ordering is preserved per key from the start.

### Week 5: Failure detection

Brokers will send periodic heartbeats to the controller, which will mark a broker as failed after a timeout and stop routing clients to it. I will test this immediately by killing, pausing, and restarting broker containers, and I will rerun these failure tests after every later stage.

### Weeks 6–7: Persistent logs and crash recovery

Each broker will maintain append-only log files on disk. I will implement message offsets and committed consumer offsets. Recovery will be tested alongside each feature: a crashed broker must rebuild its state from disk, including detecting a partially written final record, and a crashed consumer must resume from its last committed offset or deliberately replay earlier events.

### Weeks 8–10: Replication, acknowledgments, and leader failover

Partition leaders will replicate new log entries to followers, and I will track which replicas are in sync. I will define when an event becomes committed and experiment with acknowledgment requirements. Building on the failure detection from Week 5, the controller will promote an up-to-date replica when a leader crashes during active writes, and a restarted broker will catch up from the new leader. This is the most difficult part of the project, so I have allocated three weeks to it.

### Weeks 11–12: Delivery semantics and fault injection

I will build a fault-injection layer that delays, duplicates, and drops messages and acknowledgments, and that simulates network partitions between brokers. I will investigate retries, duplicate delivery, and consumer crashes, and implement idempotent producers using producer IDs and sequence numbers.

### Weeks 13–14: Scaling and evaluation

I will increase the workload from small test streams to hundreds of thousands of events while measuring latency, throughput, replication lag, duplicate events, and data loss, including how these change with the number of partitions and the acknowledgment setting.

### Week 15: Demonstration, buffer, and final report

I will build a fault-injection demonstration where brokers can be stopped or delayed while the cluster is processing events, and write up the results. This week also serves as a buffer in case earlier stages take longer than planned.

The implementation will use Python, likely with `asyncio` for concurrent networking, Docker Compose for running independent nodes, and automated tests for failure scenarios. If time permits, a final demonstration will connect several simple ML inference workers as consumers to show how the same distributed-event architecture could support an ML processing pipeline.

By the end of the project, I expect to understand not merely how to use Kafka, but why partitioned logs, replication, offsets, acknowledgment policies, and failover allow distributed event systems to remain useful in the presence of partial failures.
